# 开源前设计评审：这套“放文件 → 双击 → 出报表”的流程成立吗？

> 评审对象：Automated-Settlement-Report-Engine v1.0.0  
> 评审范围：工作流、模板生成、计算引擎、数据录入、交付方式、开源可行性  
> 结论先行：**流程成立，但它是一条“报表组装线”，不是“数据录入解决方案”。**  
> 对“模板稳定、数据已经结构化、单机/单用户、批量出 Word”的场景，它非常有效；  
> 对“模板经常变、数据来自纸/PDF/聊天、多人填报审批、复杂计费”的场景，当前形态还不够。

---

## 1. 结论：有效，但有效范围比想象中窄

这套流程真正解决的是**最后 20% 的重复劳动**：

- 把 Word 表格变成可循环的模板；
- 把 Excel 的每一行套进模板；
- 按规则算出明细和合计；
- 按固定行数分页、补空行、保留表尾合计；
- 输出一份仍然像“原公司模板”的 Word。

它不解决的是**前 80% 的问题**：

- 数据从哪里来、由谁负责、是否准确；
- 模板由谁维护、是否允许多种版式；
- 多个人如何填报、复核、审批；
- 算错了如何追溯、如何重跑、如何对账；
- 非技术用户如何在没有 Python 的电脑上稳定运行。

所以更准确的说法是：

> **它是一个很好的“结算报表编译器”，但还不是一个完整的“人工制表替代方案”。**

---

## 2. 当前流程成立的五个前提

| 前提 | 当前是否满足 | 说明 |
|---|---|---|
| 模板基本稳定，且是规则表格 | 部分满足 | 一个主表、一行表头、一行数据、一个表尾合计行最稳 |
| 数据已经结构化 | 满足 | 源数据必须是 Excel，且列名可识别 |
| 单人、单机、Windows + Office/WPS | 满足 | `一键运行.bat` 明确面向 Windows |
| 批量、低到中等复杂度 | 满足 | 适合每月几十到几百行，不适合复杂版式 |
| 结果需要“像原模板”而不是“重新设计” | 满足 | 这是相对通用报表工具的最大优势 |

只要其中一条不成立，就需要额外的产品设计，而不是继续加几个 Python 参数。

---

## 3. 最容易失效的场景（按风险排序）

### 3.1 模板几何结构变化

当前模板生成依赖：

- 一个主表格；
- `header_rows` 行表头；
- 表头下面第一行是数据行；
- 数据行不能有纵向合并；
- 表尾用“合计/总计/小计/共计”识别；
- 表格不能是浮动表格。

这在“公司固定模板”里没问题，但开源用户会拿来做：

- 多行表头 + 合并单元格；
- 一张表里分多个区块；
- 嵌套表格；
- 横向/纵向混排；
- 带条件段落、图片、页眉页脚变量的复杂模板；
- 每个客户一套版式。

**建议**：把“模板契约”写成正式文档，并提供 `make_templates.py --check` 诊断命令；不符合契约时给出“第几张表、第几行、哪条规则不满足”，而不是让用户猜。

### 3.2 数据质量

当前对源数据的校验是“能读、能转数字、缺列报错”，但没有：

- 必填校验；
- 唯一性校验（工号/编号重复）；
- 数值范围校验（数量不能为负、单价不能为 0）；
- 跨字段校验（数量 × 单价 = 金额）；
- 日期/格式校验；
- 重复行、隐藏行、公式缓存值检查；
- 异常值提示（某行金额是均值的 100 倍）。

**这是当前最大的产品缺口。** 报表引擎算得再准，输入错了，输出只会“很漂亮地错”。

### 3.3 运行环境与交付方式

`一键运行.bat` 对开发者很友好，对非技术用户仍有门槛：

- 需要安装 Python 3.10+；
- 需要联网 `pip install`，公司网络/代理可能失败；
- 可能被杀毒软件/SmartScreen 拦截；
- 控制台中文编码、路径空格、中文路径、OneDrive 同步、只读目录都可能出问题；
- 文件被 Word/WPS/Excel 占用时要用户自己理解提示。

**建议**：正式开源时提供“便携版”：

- PyInstaller/Nuitka 打成 `一键运行.exe`（one-folder，内含 Python 和依赖）；
- 保留 bat 作为开发/高级用户入口；
- 提供离线依赖包和 SHA256；
- 在干净 Windows 虚拟机、Office 2016/2019/365、WPS 上做冒烟测试；
- 明确“不需要管理员权限”。

### 3.4 结果复核与追责

当前输出是“生成即覆盖”，没有：

- 运行记录（谁、什么时候、用了哪版配置/模板/数据）；
- 输入文件哈希；
- 计算过程明细；
- 与上期报表的差异；
- 审批/复核状态；
- 旧文件备份。

**建议**：增加 `runs/<时间戳>/`：

```text
runs/20261119-231500/
  run.json          # 输入哈希、配置哈希、版本、警告、输出哈希
  计算明细.xlsx      # 每行每项的公式与结果
  结算报表.docx
```

并在覆盖已有输出前自动备份。这不是“功能”，是财务类工具的基本可信度。

### 3.5 业务语义

当前引擎的模型是：

- 基本工资 = 固定基数单价 × 固定基数 + 浮动基数单价 × 浮动基数；
- 按次 = 有数量就收一次；
- 按数量 = 单价 × 数量；
- 固定金额 = 每行固定收。

这对“补贴/计件/简单结算”够用，但对更真实的结算还不够：

- 阶梯价、封顶、保底；
- 按天/按小时折算；
- 请假、加班、补发、扣款；
- 税额、含税/不含税、多币种；
- 按项目/部门分组小计；
- 多张明细表、多个计费周期；
- 负数冲销、红冲、调整单；
- 四舍五入规则（逐项舍入 vs 合计后舍入）。

**建议**：不要急着把引擎做成“万能公式”。先把规则模型显式化：

- 计费项 = 名称 + 基数 + 单价 + 适用范围 + 舍入规则；
- 支持“调整项”（正/负）和“说明”；
- 输出“计算解释”，让用户能看懂每一项怎么来的。

### 3.6 多人与协作

当前是单机文件模型，天然不适合：

- 多人同时填同一份数据；
- 填报 → 复核 → 审批；
- 版本对比；
- 权限控制；
- 留痕。

这不是加一个 `--user` 参数能解决的。要多人协作，应该走 Web/低代码/现有办公平台，而不是继续加 bat。

### 3.7 安全与隐私

结算数据通常含姓名、工号、工资、身份证号、银行账号。当前项目：

- 不联网，数据留在本机，这是优点；
- 但没有日志脱敏、模板来源校验、压缩包炸弹防护、输出目录权限检查；
- 开源后用户可能拿不可信的 `.docx` 模板来跑。

**建议**：README 增加“安全边界”；模板/数据只从可信来源获取；日志不打印敏感字段；未来 Web 版必须做权限与审计。

## 4. 当前代码层面最值得做的改进（P0/P1）

### P0：开源前应做

| 改进 | 目的 | 建议实现 |
|---|---|---|
| 模板诊断 | 让模板问题在生成前暴露 | `make_templates.py --check`：主表数量、表头行、数据行合并、表尾关键字、浮动表 |
| 数据校验报告 | 防止“漂亮地算错” | 必填/唯一/范围/跨字段校验，生成 `数据检查报告.xlsx` |
| 运行清单 | 可追溯、可复现 | `run.json` 记录版本、输入 SHA256、配置、警告、输出 SHA256 |
| 覆盖前备份 | 防止误覆盖 | 输出已存在时先复制到 `backup/`，再原子替换 |
| 预检 | 减少“跑到一半失败” | 检查 Python、依赖、写权限、源文件、输出是否被占用 |
| 便携打包 | 降低使用门槛 | PyInstaller one-folder + 离线依赖 + `一键运行.exe` |
| 错误定位 | 让用户能自己修 | 所有错误带“文件/工作表/行/列/建议动作” |
| 测试矩阵 | 防止回归 | 至少覆盖：单表/多页/多表头/合并单元格/负数/空行/公式/日期/字体 |
| 配置版本 | 避免旧配置突然失效 | 配置加 `schema_version`，启动时迁移/提示 |
| 许可证与第三方声明 | 合规 | MIT + docxtpl/openpyxl/python-docx 的许可证说明 |

本次已落地：模板诊断（`check_template` + `make_templates.py --check`）、数据校验报告（`数据检查报告.xlsx`，错误阻止/警告放行）、覆盖前备份、`runs/<时间戳>/run.json`、便携版 exe（已实际构建并跑通）、Windows CI 工作流、22 项测试矩阵，以及生成前预览（`数据预览.xlsx`）与上期差异对比（`差异报告.xlsx`）。

仍未完成：完整预检、统一错误码、配置 `schema_version`、第三方许可证清单、`examples/` 样例目录。

### P1：开源后 1-2 个版本

- **Excel 数据验证**：由 `源数据模板.xlsx` 自动带下拉/数值/日期校验；
- **本地填报页**：一个可选的本地 Web 表单，比 Excel 更适合非财务用户；
- **模板库**：内置几张常见结算模板 + 模板契约说明；
- **多表/分组**：按部门/项目拆表、分组小计；
- **调整项**：支持正负调整、备注、原因码；
- **CI**：Windows runner 上跑测试 + 生成样例 + 检查 bat 编码。

## 5. 更好的方案：三条路线，不要混在一起做

### 路线 A：把“文件优先”做到极致（推荐作为开源主线）

适合：个人、财务/行政、单机、隐私敏感、模板固定的用户。

```text
Excel/Word 文件
   ↓
一键运行.exe（内置 Python）
   ↓
预检 → 数据校验 → 计算 → 预览 → 渲染
   ↓
结算报表.docx + 计算明细.xlsx + run.json
```

优点：

- 不需要服务器；
- 数据不出本机；
- 保留原 Word 模板；
- 开源易传播；
- 当前代码 80% 可复用。

关键不是再加功能，而是把**预检、校验、预览、追溯、打包**做扎实。

### 路线 B：本地 Web / 团队版

适合：多人填报、复核、审批、模板集中管理。

```text
浏览器表单 / Excel 上传
   ↓
FastAPI + SQLite/PostgreSQL
   ↓
模板库 + 规则库 + 任务队列
   ↓
审批 → 渲染 → 归档
```

优点：

- 真正的多人协作；
- 数据集中、权限清晰；
- 可以做审批流和审计；
- 未来可接 ERP/飞书/钉钉/企业微信。

代价：

- 部署、备份、权限、升级都变成产品问题；
- 不再是“双击 bat”；
- 开源维护成本显著上升。

**建议**：不要在第一版就做。等文件版有稳定用户，再把 `settlement` 当核心库，套一个薄 Web 层。

### 路线 C：寄生在现有办公平台上

适合：已经在用 Microsoft 365 / 飞书 / 钉钉 / 企业微信的团队。

- Microsoft 365：Excel/SharePoint + Power Automate + Word 模板；
- 飞书/钉钉/企业微信：多维表格 + 表单 + 审批 + 文档生成；
- 低代码：简道云/明道云/氚云等。

优点：上手快、协作/权限/移动端现成。  
缺点：平台锁定、复杂模板能力有限、按人头收费。

**判断**：如果用户已经在这些平台上，最佳方案往往不是“再装一个 Python 工具”，而是“把规则做成平台里的一个自动化流程”。本项目可以作为离线/私有化补充，而不是替代。

### 路线 D：复杂模板换成专业文档组装引擎

`docxtpl` 适合“表格循环 + 占位符”，不适合：

- 复杂条件版式；
- 多级编号、条款库；
- 交叉引用、目录；
- 高保真 PDF；
- 大规模并发渲染。

可评估：HotDocs、Docmosis、Plumsail Documents、Windward、Aspose.Words。  
代价是许可费/供应商锁定；开源项目应把渲染层做成可替换接口，而不是把 docxtpl 写死。

## 6. 数据录入才是真瓶颈：可以借鉴的领域

| 领域 | 可借鉴的做法 | 用到本项目 |
|---|---|---|
| 会计/ERP | 控制总数、对账、期间关闭、审计轨迹、职责分离 | 生成前核对行数/总额；输出 run.json；覆盖前备份 |
| 薪酬 | 收入/扣减项、生效日期、折算、补发、工资条解释 | 计费项模型、调整项、计算解释 |
| 电信计费 | 用量 → 批价 → 账单、价格计划、调整/抵扣、争议处理 | 规则与渲染分离；异常队列；可重算 |
| 保险理赔 | 规则引擎、资格校验、异常队列、可解释结果 | 数据校验报告；每条规则给出原因 |
| 数据工程/ETL | Schema 契约、校验、幂等、血缘、重放、死信队列 | 输入哈希、可重跑、失败不覆盖、日志 |
| 编译器 | 解析 → 语义检查 → 代码生成；带位置的诊断 | 模板解析 → 字段映射检查 → 渲染；错误带行列 |
| 文档组装 | 访谈式采集、条款库、条件内容 | 可选的表单采集；模板条件段 |
| 物流/现场作业 | 条码/二维码、移动表单、离线同步、主数据 | 扫码录入工号/单号；主数据校验 |
| 表格风险管理 | 单元格保护、数据验证、版本、校验和 | 源数据模板加验证；配置/输出哈希 |
| 交互设计 | 渐进披露、预览后提交、撤销、明确错误 | 先预览再生成；失败可恢复 |

其中最关键的三条：

1. **控制总数**：生成前先算“应有行数/总额”，和源数据对一遍；对不上就停下来。
2. **幂等与可重放**：同样的输入必须得到同样的输出；失败不能留下半个文件。
3. **可解释**：每一行的每一项，用户都能看懂“为什么是这个数”。

## 9. 一句话总结

**这套流程值得开源，但要把定位说清楚：**

> 它不是“替代 Excel 数据录入”的平台，  
> 而是“把已经结构化的数据，稳定、可追溯地变成公司格式 Word 报表”的最后一公里。

先把最后一公里做扎实：**模板契约、数据校验、预览、追溯、便携打包**。  
等到有真实用户提出“多人填报/审批/系统集成”，再考虑 Web 版；不要反过来先造一个平台，再找场景。
